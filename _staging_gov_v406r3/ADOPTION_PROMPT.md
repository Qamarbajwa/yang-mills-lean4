# Universal bounded adoption prompt

Use this prompt only after the owner has identified the target project and authorized governance adoption. The universal package itself remains unbound and project-neutral.

---

Apply Universal Governance Minimal 4.0.6-r3 to the target project as one bounded, reversible adoption candidate.

First inspect the actual project. Determine whether this is NEW_PROJECT, MID_PROJECT_UNGOVERNED or MIGRATION_GOVERNED. Establish repository/root identity, branch/HEAD or equivalent candidate identity, dirty state, current instructions, current governance if any, project intent, architecture, capability scope, tests, evidence, external systems, blockers, release state, reserved actions and available independent review capability. Do not infer missing facts from this template.

Treat this package as proposed universal governance until project-specific binding, required verification and cutover are complete. Do not overwrite active governance or state blindly. Prepare the new three-authority candidate in non-active staging while preserving the current truthful project state.

Populate `governance/GOVERNANCE.md`, `governance/PROJECT_DIRECTION.md` and `governance/PROJECT_STATE.yaml` only from the target project's actual facts. Bind the evidence companion to an actual target-project path/reference (copy/adapt `EVIDENCE_AND_MIGRATION.md` or map to an equivalent reviewed source) and record that reference in PROJECT_STATE; copying only the three entry files must not leave a dangling evidence vocabulary. Do not import names, paths, ports, capability IDs, provider choices, model assignments, statuses, screenshots, test results or release claims from any unrelated project or example.

Preserve stronger existing safety, security, legal, financial, independent-review and release gates. Preserve failures, negative evidence, unresolved unknowns and NO-GO conditions. Governance migration must not turn missing evidence into PASS or an unverified legacy capability into VERIFIED.

Reconcile existing detailed specifications rather than duplicating them. Keep design systems, API contracts, schemas, data models, workflow diagrams, component catalogs, tests and evidence as narrowly delegated technical sources when they already exist. The three active governance files are entry authorities, not containers for every technical detail.

For user-facing capabilities, verify complete vertical scope: purpose, actors, user journeys, UI surfaces, permissions, backend behavior, data/state, external systems, responsive/accessibility requirements where applicable, failure/recovery states and evidence. A backend capability intended for a user/admin surface must not remain unintentionally hidden; a UI surface must not masquerade as complete without real authorized backend behavior.

For launched products, bind intended operating outcomes, applicable privacy-safe feedback/telemetry, incidents, service reliability, security/quality assurance, cost/maintenance, capability exposure and retirement authority. Distinguish PRIMARY/SECONDARY/ON_DEMAND discoverability from ACTIVE/SUSPENDED/RETIRED availability. Preserve essential and user-pinned access, dependencies, existing user data and applicable contractual/privacy obligations. Do not infer live metrics or adoption decisions from template text; unlaunched projects may define intended observation without fabricated evidence.

For external systems, distinguish code presence, mock/fixture evidence, sandbox or representative evidence, real-environment evidence, production configuration, activation authority and production observation. Define authenticity, idempotency, retry/order semantics, state ownership, reconciliation, degraded behavior, recovery and kill-switch behavior where applicable.

Bind consequential claims to exact frozen candidate/environment/scope evidence. Apply the explicit role matrix and project-bound permitted combinations: do not let a writer become its own independent acceptor; do not let IND1 silently satisfy an IND2 requirement. Missing required review blocks the acceptance claim, not all authorized preparation or unrelated work. Test stale state-write rejection, dependency gates, reserved-action boundaries, failure-history retention, candidate drift and rollback/recovery. Also test stable-architecture protection, characterize-before-refactor behavior, intent-fidelity review, regression protection, bounded retries/spend/concurrency where applicable, untrusted-instruction resistance, secret leakage prevention, operational diagnosability and nondeterministic outcome acceptance by invariants rather than identical output. Do not weaken tests to make adoption pass.

Before cutover, freeze the candidate, re-read the target project's current state and affected files, resolve drift, obtain required qualified independent review/acceptance, and verify that the cutover activates one current project-level governance set without destroying historical provenance or unrelated work.

After accepted cutover, archive or deactivate superseded governance according to repository constraints. Archive is historical evidence, not operational instruction. Verify entry points and consumers resolve to the new active governance.

Then continue the next dependency-satisfied authorized product objective autonomously. Report only the actual project/candidate identity, adoption status, checks performed, evidence/review references, remaining blockers, reserved actions and next eligible objective. Governance adoption does not itself imply product completion, release eligibility or deployment authorization.

## Runtime authorization binding (mandatory where live effects exist)

`validateReleaseState` only validates shape and internal consistency, not current authority. Bind exact frozen candidate/environment/scope/action and a trusted clock to a project-specific authorization gate checking live grant existence, freshness, revocation, consumption and applicable permissions. Never treat source-template or package-verifier PASS as authorization for an external action. Preserve the original candidate/review history; do not require human technical sign-off when qualified AI technical reviewers/acceptors meet the bound independence and legal conditions.
