# Project direction — UNBOUND TEMPLATE

Governance version: 4.0.6-r3. This file defines intended scope, not live progress. Populate from the target project's actual owner decisions; do not activate placeholders.

## Intent and boundaries

Record project identity, purpose, desired outcomes, users, non-goals, unacceptable outcomes, supported release scope and owner/business/legal/exposure boundaries. Separate milestone completion from release and deployment.

## Delegated source map

For each existing source record path or resource ID, narrow role, owner, applicable version/decision and conflict/supersession rule. Required where applicable: detailed design system, selected images/manifest, route family matrix, workflow diagrams, capability/preservation contracts, API/data contracts, architecture, evidence registries and recovery procedures. Do not rewrite them into this file or treat historical inventory as current runtime proof.

## Capability contracts and actors

Use existing stable IDs. For each supported capability define the owner/product outcome it is meant to achieve, actors and permitted/forbidden actions, user journey, entry surface or NONE_BY_DESIGN, service/data ownership, outputs, persistence, external effects, states, failure/recovery, accessibility, critical invariants and acceptance evidence. When performance/concurrency/endurance can materially affect the outcome, define the expected operating envelope or explicitly state that the concern is N/A with rationale. Maintain intended actor-by-capability coverage. Exposure classification does not grant permission to expose internal functionality.

## Architecture and integrations

Describe actual intended components and state boundaries. Map surface → API → authorization → service/job → data/external system → reconciliation → visible outcome. Define external activation authority and operational requirements. Replace sample diagrams with meaningful project topology; do not invent dates or progress colors.

## Shared presentation, if applicable

For projects with a UI, reference the actual accepted design-system/component source, visual character, supported devices/themes/locales/accessibility requirements, roles and intended role-by-capability/capability-by-surface coverage. Keep implementation-level tokens, component APIs, route inventories and detailed visual procedures in existing or narrowly delegated technical sources rather than duplicating them here. These are intended requirements, not live PASS/FAIL; current conversion/visual evidence belongs in State/delegated evidence. Projects without a UI mark this concern N/A once with rationale rather than inheriting browser/route/component obligations.

## Roadmap and decisions

Define bounded objectives, dependencies, capability IDs and acceptance outcomes. Preserve stable historical contract IDs. Record current decisions, their demonstrated reason and what they supersede. Stable accepted architecture should not be replaced for preference alone; consequential rewrites identify the problem being solved, affected consumers and intended compatibility/migration outcome. Execution eligibility/status belongs in state; intended ordering belongs here. Reserve genuine owner decisions only, never routine technical certification.

## Post-launch outcomes and capability lifecycle (when applicable)

Define intended customer/task outcomes, relevant user cohorts, meaningful usage/quality/security/cost signals, observation boundaries, and policy for essential, user-pinned, on-demand, suspended and retired capabilities. Define who may decide material exposure, entitlement, support, data and service changes; differentiate planned visibility from actual availability. Avoid invented numeric thresholds or collecting data without the applicable privacy basis. No operational metrics/PASS claims live here; they belong in State or delegated evidence. Products not yet launched may define intended outcomes without inventing observations.

## Completion

Define exact supported capabilities, required/target environments for acceptance and milestone boundaries. Completion requires functional journeys, frontend/backend/external parity where applicable, truthful states, applicable recovery/accessibility/security evidence, required independent acceptance and no unresolved critical defect in the claimed scope. Release eligibility and deployment are separate.

## Update rule

Change direction for intent, architecture, contract, reference or roadmap changes. Revalidate affected consumers and evidence. Do not edit this file for routine PASS/FAIL updates; use PROJECT_STATE.yaml. Preserve historical decisions by reference, without creating competing active rules.
